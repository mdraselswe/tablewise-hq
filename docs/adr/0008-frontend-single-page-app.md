# ADR 0008: Frontend as a React single-page app with server state in TanStack Query

- Status: accepted
- Date: 2026-11-25

## Context

The brief requires React. The users are HQ staff on desktops and cashiers and cooks on tablets at the counter, all signed in. There are no public pages to index, and the screens that matter (POS, kitchen display, live dashboard) stay open for hours and change many times a minute. The frontend must keep up with live data, survive flaky outlet Wi-Fi, and keep working if the backend is split into services later.

## Decision

- **A client-rendered single-page app built with Vite**, served as static files from the same origin as the API. Every route is its own lazy chunk; React, data and UI libraries go in separate long-cached vendor chunks.
- **TanStack Query owns all server state.** Query keys mirror the backend modules (`catalog`, `inventory`, `sales`, ...), so a change invalidates exactly the screens that show it. Live SSE events patch cached data directly and only debounce refetches for derived figures such as report totals. There is no global client store; the little client state there is (cart, theme) stays local.
- **URL-driven UI state.** Dialogs, tabs and filters live in the query string, so reload, back and deep links work.
- **Own the components.** Primitives come from Base UI (focus, keyboard, ARIA) and are styled in `components/ui` with Tailwind CSS 4 design tokens in one file. The components are written in the shadcn style (source in the repo, `cva` variants) but are not generated by the shadcn CLI.
- **React Router** (data router) for nested layouts, role guards and route-level code splitting.

## Alternatives considered

- **Next.js or another SSR framework.** Server rendering helps SEO and first paint for anonymous visitors, neither of which exists here: every page sits behind a login and is used for hours. SSR would add a Node rendering tier, a second server to scale and a split between server and client components, while the API already is the server. A static SPA deploys anywhere, caches perfectly and can later be wrapped for offline use (see the offline POS strategy in [architecture.md](../architecture.md)).
- **Redux Toolkit / Zustand for server data.** They would duplicate what TanStack Query provides (caching, deduplication, background refresh, retries, optimistic updates) with hand-written code. RTK Query is close, but TanStack Query has the simpler cache-patching API that the realtime layer relies on.
- **A ready-made component kit (MUI, Ant Design, Chakra).** Faster to start, but heavy, hard to restyle beyond its theme and recognisable at a glance. Owning thin components over accessible primitives keeps the bundle small and the look specific to this product.
- **A chart library (Recharts, Chart.js).** The dashboard needs one area chart and a few sparklines; small SVG components avoid a 100 kB+ dependency and read the design tokens directly.

## Consequences

- One origin for app and API: the session cookie is first-party, no CORS, and one Docker image serves both.
- The first load downloads only the shell and the current page; deploys usually invalidate only app chunks. A tab left open across a deploy can miss an old chunk, so the error page detects failed dynamic imports and offers a reload.
- Search engines see an empty shell, which is acceptable for an internal tool.
- The `api/` layer is the only place that knows endpoints. If a backend module becomes its own service, only its base URL changes.
